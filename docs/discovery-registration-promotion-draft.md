# 内容结构生成、来源登记与语义晋升草案

状态：讨论草案，未实现。内容发现的单次 Producer 已实现；本文提出其后来源层契约的修订，
不表示当前 Domain 构造器或 SQLite 已经支持接受和登记。既有输入、提案和验证接口以
[`discovery-proposal-v3.md`](discovery-proposal-v3.md) 为准；数学上下文、语义和对齐的上位模型见
工作区 [`EMIR 规范`](../../docs/rdtx/emir-source-semantics-alignment.md)。

## 1. 目标与基本决策

用户选定 Markdown 内容后，系统应能发现其中的定义、命题、证明、习题等结构，经验证和
接受决策后登记为可定位、可引用的来源节点。数学上下文和全局对齐可以后续按需补充。

本草案将过去笼统的“两次晋升”细化为：

1. **内容结构生成**：LLM 提出原文单元、关系、引用与覆盖情况。
2. **来源登记**：程序将已接受的发现规范化为具有稳定身份的来源节点和超边。
3. **数学语义构建与对齐**：在上下文和已有数学知识的支持下，进一步解释、关联和复用。

完整 DialectScope 不应是所有来源节点入图的前置条件。一个命题可以已经定位并可被引用，
同时其符号含义仍待解释。自动接受、人工审核、来源登记和数学可信性必须分别表达。

## 2. 每个阶段的信息增量

| 阶段 | 输入信息 | 新增结果 | 主要执行者 |
| --- | --- | --- | --- |
| 输入构建 | 用户选区、不可变 Markdown、锚点、Artifact 与 Conversion 信息 | 有版本和指纹的 DiscoveryInput | 程序 |
| 内容发现 | DiscoveryInput、版本化 prompt、输出契约 | 单元及关系候选、引用、issues、coverage | LLM |
| 确定性验证 | Proposal、原始输入、限制与规则 | 获授权的位置、闭合关系、诊断、complete/partial | 程序 |
| 接受决策 | 已验证提案、用户选择的发布策略或审核结果 | 接受范围及决策来源 | 用户或策略 |
| 来源登记 | 接受结果、系统来源信息、已有来源记录查询结果 | 稳定 ID、来源定位、规范化关系、登记记录 | 程序 |
| 上下文化与局部语义 | 来源单元、相关原文、继承约定及已有局部解释 | DialectScope、符号绑定、命题及证明的局部解释 | LLM 辅助，程序验证 |
| 全局对齐与 R/D/T/X 构建 | 局部语义、检索得到的已有数学实体、必要的数学工具结果 | 对齐关系、复用或新增的数学实体、R/D/T/X 实例及证据 | LLM 辅助，程序验证和提交 |

校验主要检查已有信息是否满足约束，不会自动补出数学含义。query 提供可复用对象和判断依据，
也不能直接证明两个概念等价。后续阶段的信息增量还可能来自前文定义、章节约定，以及对材料
进一步推理形成的解释。模型推断必须区别于原文明示事实，并保留依据和未解决问题。

当前 DiscoveryInput v2 的 context 必须为空。后续补上下文应构造独立的语义任务输入，或显式
升级 DiscoveryInput 契约，不能在不改变指纹和授权范围的情况下向现有输入追加材料。

## 3. 最小处理流程

```text
Markdown 选区 → DiscoveryInput → LLM → DiscoveryProposal
                                              ↓
                                      确定性验证
                                     ↙          ↘
                           诊断 / 有界修订       ValidatedProposal
                                                     ↓
                                             用户或策略接受
                                                     ↓
                                          来源登记计划（内存）
                                                     ↓
                                           校验 + 原子提交
                                                     ↓
                                         可浏览的来源节点与超边
                                                     ↓ 按需
                                  上下文化 → 局部语义 → 全局对齐
                                                     ↓ 按需
                                             R / D / T / X
```

失败、等待审核或存在登记冲突时，保留提案及诊断供查看，不报告已完成登记。
语义解释失败不会撤销已经成立的原文定位事实；它留下的是后续任务的问题和状态。

### 3.1 内容结构生成与接受

Proposal 中的 temp_id 只在该提案内有效。模型不分配全局稳定身份、不指定数据库路径，
也不因知道其他实体的名称而获得引用它们的权限。

程序先完成 JSON 解码与现有确定性验证，再应用接受策略：

- 人工审核模式：经用户确认的提案或闭合子集可被接受。
- 自动模式：只有通过验证且满足用户预先设定条件的结果才可被策略接受。
- partial 可以被明确接受，但必须保留未处理区域、截断和其他问题，不能据此标记整个任务完成。

“accepted candidate”在本文表示接受决策的结果，不是新的数学实体类型，也不自动对应
TrustRecord 的人工审核状态。需记录决策者是用户还是策略、接受了哪个提案版本和范围。
如果用户编辑提案，或排除了关系端点、父单元等，变更后的结果必须重新检查引用闭合和覆盖说明。

### 3.2 来源登记

来源登记不要求再调用一次 LLM。注册器使用已规范化的选择器和受信任来源信息完成：

1. 核对输入快照、接受范围和当前数据库状态，查找已有来源记录。
2. 创建或复用 SourceSpan；定位到 Markdown 的 UTF-8 半开字节区间并绑定不可变 Artifact。
3. 分配或复用来源单元稳定 ID，保存提案 temp_id 到该 ID 的映射。
4. 将单元关系转换成稳定端点及证据端点；保存真实的 parent 和未解决引用。
5. 检查端点存在性、类型、冲突及预期 revision，原子提交该闭合批次及登记结果。

来源关系例如 `proves`，此时表达“原文将这段内容呈现为该命题的证明”；这不等于证明已经
被 Lean 检查。图投影应保留这一关系所属的来源层和独立可信状态。

可以使用一个暂名 `SourceRegistrationPlan` 的内存值携带实体、关系、复用映射、诊断和提交
前置条件。它是受控写入的准备结果，不需要单独的持久化对象体系。底层可以复用 MapPatch
契约；通用提交器与相关 repository 尚需实现，不能把已有 MapPatch 类型视为已存在的写入服务。

### 3.3 数学语义构建与对齐

后续用户可以选取已登记的来源节点，发起更深入的数学解析：

- 读取必要的定义、符号约定、假设及编号环境，创建或继承 DialectScope。
- 表达局部符号、量词、前提、结论和推导；证明局部状态由 ProofContext/ProofState 承担。
- 查询已有数学实体，提出复用、等价、特化、表述转换或不匹配的判断，并保存依据。
- 具备足够结构和证据时再构造 R/D/T/X，不要求每个来源单元必然生成这些实例。
- 需要更高可信性时附加 Lean 等工具产生的检查证据，并记录其实际检查范围。

来源节点继续保留原始身份。一本教材的来源单元与另一本教材的来源单元可以指向同一全局
数学实体，但不能因此删除或合并两处来源事实。同一来源也允许存在多个待比较的语义解释。

## 4. 登记、去重与查询的边界

登记查询主要限于同一来源的已有记录。内容发现之前的缓存查询则用于节约模型调用，两者
解决的问题不同：登记幂等不能避免已经发生的重复推理费用。

| 情况 | 建议处理 |
| --- | --- |
| 同一接受批次重复提交 | 返回既有提交结果及稳定 ID，不重复登记 |
| 同一输入及兼容 producer 配置再次请求 | 可复用已有发现结果；接受策略单独应用 |
| 相同 Artifact 和范围发现语义角色相容的单元 | 查找已有身份，复用或提出有审计的新 revision |
| 边界或类型不一致、仅部分重叠 | 产生冲突诊断；不凭范围相交自动合并或覆盖 |
| 同一 PDF 的另一份 Marker 转换 | 字节位置不可直接比较；有可靠来源映射时再核对 |
| 不同教材表达相同数学概念 | 保留各自来源节点，在数学语义层对齐 |

Artifact、规范化范围、来源角色及必要的所属上下文是候选查找依据，不承诺它们天然构成
通用唯一键。同一段文字可能承担多个数学言语行为，边界也可能被后续修正。
稳定 ID 不应绑定 temp_id 或单次模型输出；可变标题、分类和切分判断应有修订策略。

Conversion 保留解析来源和 PDF 回链依据；相同 Markdown 字节由不同转换产生时，系统须区分
可复用的文本位置与各自的溯源路径，不因哈希相同而丢掉转换证据。

输入指纹只是材料身份。精确缓存还需考虑 prompt、producer/输出契约、模型配置及影响输出的
参数等兼容性条件。重叠选区和跨转换的部分复用作为后续优化，首版不承诺自动解决。

## 5. 状态与身份原则

以下维度必须分开表达，具体字段名留待契约修订：

| 维度 | 回答的问题 |
| --- | --- |
| 运行与覆盖 | 调用是否完成？请求范围还有哪些内容未处理？ |
| 确定性验证 | 定位、引用、类型和结构是否满足当前规则？ |
| 接受决策 | 谁允许哪些结果进入来源图，是用户还是策略？ |
| 登记结果 | 事务是否提交，创建或复用了哪些稳定实体？ |
| 上下文与语义成熟度 | 符号、假设及解释是否已建立，缺少什么？ |
| 数学可信性 | 哪些断言经过人工检查或形式化验证？ |

接受不保证登记成功；登记成功不保证语义完整；语义已构建不保证形式化证明成立。
“正式来源节点”仅指遵循领域契约并已受控登记的来源记录，不意味着数学结论已经成为权威。

不为 generated、accepted、registered、contextualized 各建一份相同的来源节点。原始提案与
运行事实用于审计；登记映射连接到持久来源身份。后续新增解释、对齐或证据通常通过关系关联
到该来源身份，只有来源单元本身的描述改变时才需要修订它。

## 6. 对现有 Domain 的待实施修订

当前 `SourceSemanticUnit` 必须提供 source_edition 和 dialect_scope；当前 SourceSpan 的
构造也尚未支持所需的独立 Markdown 定位。直接将 AcceptedCandidate 交给现有构造器并不能
完成本文的登记流程。需要先修订这些约束：

1. 来源定位必须至少有一种真实有效的定位方式。Markdown Artifact 与字节区间可以独立成立；
   只在拥有可靠映射时附加 PDF 页面或坐标，不能用转换总页范围充当精确定位。
2. 未解析的 Edition 不阻断来源登记。Artifact 来源必须可回溯，书目归属可后续补充，不能生成
   虚假 Edition 来满足必填字段。
3. 完整 DialectScope 不再是登记前置条件。未构建的上下文须明确标记为尚未解析，而非“空环境”。
   可选引用或独立的上下文化关系如何表达，在实施时选择一种统一方案。
4. 缺失完整性、未解决引用和继承环境不会自动获得 checked、resolved 或人工 accepted 标记。
5. 登记单元与关系需增加对应 SQLite 写入/读取和 projector；现有发现验证器不能替代这些设施。

上述修订应与现有 fixture、来源层规范一起评审。本次文档仅给出方向，不预先冻结新的字段、
表结构或自动合并算法，也不修改当前构造器。

## 7. 最小案例

Markdown 包含“习题 1：证明常数数列收敛”和随后的一段解答。

1. LLM 输出 `u1: problem`、`u2: solution` 和 `solves(u2, u1)`，各自附选择器及证据。
2. 程序解析其真实字节区间、验证关系和 coverage；用户或自动策略接受该版本结果。
3. 注册器创建或复用两个来源单元及其 SourceSpan，把关系端点替换为稳定 ID，并在同一事务
   中提交。图上已可点击习题、解答和来源关系，回到相应 Markdown 区域。
4. 此时数列符号和极限定义可以仍未解析，来源节点不需要空壳 DialectScope。
5. 后续语义任务读取该书的极限定义和约定，解释解答中的量词及 N 的选择，并查询已有的
   常数数列、收敛定义和相关定理进行对齐。产生的语义对象和证据关联回原有来源单元。
6. 再次发现完全相同的习题时，登记复用已有来源身份；另一本书中的同类习题保留独立来源，
   是否共享数学命题、方法或 R，由后续语义解释与对齐判断。

## 8. 实施与验收顺序

Schema、版本化 prompt 和单次 Producer 已完成；下一步完成发现结果与接受记录持久化，随后修订
上述必要 Domain 约束，实现确定性登记与来源图投影。上下文化和全局对齐作为后续可独立
调用的任务逐步接入。

验收重点：接受结果无 DialectScope 也可受控登记；登记后原文定位可复查；重放不重复创建；
冲突不静默覆盖；缺失上下文保持可见；新增语义解释不复制来源节点；两个教材能够共享数学
实体而保留各自来源；自动接受不会被显示为人工审核或形式化通过。
