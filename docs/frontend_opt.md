## 逐项判断

### 1. 景观图包含材料图和来源图

这是合理的底层设计，但不适合作为用户对“三种视图”的最终理解。

材料图、来源图、景观图仍然有技术意义：

- 材料图：回答“有哪些 PDF、Markdown、转换任务”；
- 来源图：回答“材料中有哪些内容单元、原文范围和来源关系”；
- 景观图：回答“材料、来源、语义、形式化对象之间如何连接”。

但它们不应该继续表现为三个完全独立的地图页面。更合适的是：

> 一张统一数学地图 + 若干过滤器和聚焦预设。

例如：

- 总览；
- 材料；
- 来源内容；
- 语义对象；
- 形式化对象；
- 证据；
- 当前节点的邻域。

这些是“显示哪些对象”的选择，而不是三个不同地图。

因此，你提出的“合一后按节点类型和关系类型过滤”是值得采纳的。

### 2. “材料图 / 来源图 / 景观图”应改成统一地图

我建议保留内部的 `ProjectionLens`，但隐藏其实现含义。前端改成：

- 顶部主标题统一为“数学地图”；
- 提供“视图预设”或“显示范围”；
- 允许独立控制节点层和关系层；
- 当前选择、来源聚焦、证据显示都作为临时过滤状态。

例如：

```text
数学地图

显示节点：
☑ PDF / Markdown
☑ 内容单元
☐ 原文证据
☑ 语义对象
☐ 形式化对象

显示关系：
☑ 来源于
☑ 包含
☑ 引用
☐ 证明
☐ 对齐

聚焦：
[全部] [当前来源] [当前节点邻域]
```

这样既保留了底层投影的清晰性，也避免用户必须理解“材料图”和“来源图”的概念区别。

这里需要注意：不能默认展示整张全量景观图。景观图在数据量增长后会迅速变成低可读性的“毛线团”。统一地图应默认使用：

- 当前节点邻域；
- 当前来源范围；
- 当前章节；
- 用户选定的层级组合。

“全景总览”应该是一个可主动进入的模式，而不是默认工作区。

### 3. 按来源聚焦非常有价值

这一点我认为应该优先实现。

用户真正常见的操作不是“查看所有来源节点”，而是：

> 我想看看这本书贡献了哪些内容，以及这些内容后来连接到了哪些数学对象。

可以把一个 `SourceArtifact` 作为聚焦根节点，沿着来源链展开：

```text
PDF
 └─ ConversionRun
     └─ Markdown
         └─ SourceSpan
             └─ SourceSemanticUnit
                 └─ Local/Global Semantic Object
```

但不建议仅依赖双击作为唯一入口。更清晰的交互是：

- 点击：选择节点并打开 Inspector；
- 双击：进入该节点的局部邻域；
- 右键菜单：`聚焦此来源`、`展开一层`、`展开全部后代`；
- Inspector 中提供明确按钮：`以此来源为中心查看`。

聚焦时还应允许选择：

- 展开深度：1 层、2 层、全部；
- 包含哪些层：来源、语义、形式化；
- 是否显示证据范围；
- 是否显示关系标签。

否则一个 PDF 关联几百个单元时，双击会直接重新制造一张不可读的大图。

### 4. 来源图外的大方框没有实际数学意义

你的猜测不正确。当前方框不是“某个来源下所有派生节点的区域”，而是投影实现中的 `ProjectionGroup`。

来源投影中创建了一个名为“来源图”的分组：

```rust
ProjectionGroup::new(group_id, "来源图", ViewLayer::Source, None)
```

景观图中则创建了 `source-map-landscape` 分组。Cytoscape 将这个分组渲染成了一个巨大的 compound node，所以用户看到的是包住所有节点的矩形。

也就是说，它目前只是：

> “这些节点属于同一个投影批次”的渲染容器。

它不是：

- 数学对象；
- 来源范围；
- PDF；
- 章节；
- 内容层级；
- 语义区域。

因此当前的视觉表达会误导用户，应该调整：

1. 默认不把投影分组渲染成可见节点；
2. 如果需要分区，只使用淡色背景带或顶部标签；
3. 只有在用户开启“显示分组边界”时才显示矩形；
4. 真正的来源聚焦区域应根据 `SourceArtifact` 动态生成，而不是使用一个全局 `"来源图"` 分组。

这项修改主要属于投影渲染层，不需要修改 EMIR 核心模型。

### 5. 关系为什么要显示成一个节点

这是当前实现中最明显的“内部结构泄露”。

`GraphProjection` 支持超边，而 Cytoscape 的基本边是二元边。为了把一个多端点关系投影到 Cytoscape，当前 `IncidenceGraph::project` 把关系转换成了一个菱形节点，再将各端点连接到这个节点。实现见 [`incidence.rs`](/Users/wangjiajie/software/lean4_exp/mathscape/crates/mathscape-graph/src/incidence.rs:160)。

这在数学数据结构上是合理的，因为：

```text
A ──┐
B ──┼── 关系 R
C ──┘
```

能够保留超边的：

- 关系身份；
- 端点角色；
- ordinal；
- 有向性；
- 多元关系结构。

但是对于普通用户来说，菱形节点会被理解成“又一个数学对象”，而不是“连接这些对象的关系”。

因此我建议分为两个渲染模式。

#### 默认模式：语义边模式

关系不作为可见节点，而表现为：

- 带标签的边；
- 边上的关系类型徽标；
- 鼠标悬停时显示关系名称和端点角色；
- 点击边时在 Inspector 中显示完整关系详情。

例如：

```text
定义 3.3.1 ──引用──> 例 3.3.2
```

二元关系可以直接画成一条边。

多元关系可以采用：

- 边束；
- 隐藏的 junction 节点；
- 关系标签浮层；
- 点击后展开端点列表。

#### 高级模式：超边调试模式

保留现在的菱形关系节点，用于：

- 调试超图结构；
- 检查端点和角色；
- 查看复杂的多元关系；
- 开发者或高级用户分析。

这样既不破坏当前 `IncidenceGraph` 数据契约，又能让普通用户看到更自然的图。

## 我建议采用的总体设计

把现在的三种页面改为：

```text
数学地图
├── 显示预设
│   ├── 总览
│   ├── 来源
│   ├── 语义
│   ├── 形式化
│   └── 证据
├── 节点过滤
├── 关系过滤
├── 聚焦来源
├── 聚焦节点邻域
└── 渲染模式
    ├── 语义边
    └── 超边调试
```

底层仍然保留：

- `ProjectionLens`；
- `ViewLayer`；
- `ProjectionGroup`；
- `ProjectionRelation`；
- `IncidenceGraph`。

但这些属于查询和渲染协议，不应直接成为用户必须理解的概念。

## 五点的采纳优先级

我建议全部采纳，但顺序如下：

1. **隐藏或弱化来源图外的大方框**；
2. **统一类型名称、关系名称和图例**；
3. **把关系节点改成默认不可见的语义边模式**；
4. **加入按来源聚焦和后代展开**；
5. **把三种视图改造成统一地图的过滤预设**；
6. **最后再优化全景布局、局部邻域和大图性能**。

其中第 1、2、3 项是立即可见的可用性修复；第 4、5 项是信息架构重构；第 6 项则是规模化后必须处理的问题。

总体上，你的判断是正确的：当前问题不是地图数据不足，而是渲染层把“投影容器”和“超边编码方式”误当成了数学景观本身。下一步应该优先优化统一地图和局部聚焦，而不是继续增加新的视图名称。
