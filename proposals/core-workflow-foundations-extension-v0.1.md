# 核心工作流接入前的模型与基础设施扩展草案 v0.1

状态：讨论草案，2026-10-16。本文提出候选规则、首版简化假设和验证路线，不表示这些能力已经实现，也不直接替换 EMIR/R/D/T/X 规范。文中的类型、接口和状态名称用于讨论，实施前应收敛为版本化契约。

评审修订：2026-10-16 根据用户转交的 Argon 七项建议调整，主要改变上下文、暂存候选、产物分流、证明步骤、并发和学习记录。逐项判断及未照搬的部分见 §13；本文保留 v0.1 文件名，仍供讨论，不视为用户已批准实施。

## 1. 目的与设计立场

Mathscape 的两个软件期望是：围绕长期问题形成学习路线，以及围绕具体困惑展开调查、解释和练习。它们描述用户希望获得的帮助；实际流程、界面和对象模型需要由真实任务验证，不能提前固定成两条不可变的流水线。

当前需要一个“接入核心 workflow 前的补漏”阶段：把材料、手稿、来源图和登记治理连接成 Agent 可可靠使用的能力，并补足生成内容、用户反馈、数学身份和生命周期的契约。删除语义属于这一阶段，但不能独立承担全部设计。

建议采用的原则：

1. 调查按用户问题推进，材料与地图按需读取和扩展；完整扫描一章不是开始解释的前提。
2. 每次持久提交都明确依据、上下文、版本、权限及未解决事项；局部工作不降低相应对象的有效性要求。
3. 外部 harness 可以组织执行，Mathscape 保有任务、反馈、知识对象、接受决定和提交回执的权威记录。
4. 单用户首版只运行一轮 Agent 调查，知识提交串行化；探索期间允许人工编辑，提交时校验版本和结构条件，不引入多 Agent 并发写图与自动冲突合并。
5. 第一轮只实现能支撑验收场景的对象种类和工具；名字出现在 EMIR 枚举中，不代表已经需要完整实现。

参考：[软件期望与现状](../docs/architecture.md)、[专家讨论原稿](core-workflow-design.md)、[EMIR](../../docs/rdtx/emir-source-semantics-alignment.md)、[R/D/T/X](../../docs/rdtx/rdtx-map-construction-spec.md)、[手写提案](handwriting-input-infrastructure-v1.md)。专家讨论作为输入材料保留，本文负责提出 Mathscape 自身的候选决策。

## 2. 现有基础与真正缺口

EMIR 已包含 `created_by`、`generation_run`、Artifact、`Evidence.llm_analysis`、候选语义、带作用域 Alignment，以及稳定身份与修订分离。因此不能把问题概括为“原规范完全没有 Agent 产物”。缺口是：用户输入、Agent 原创内容、调查过程与正式数学对象之间，还没有统一的应用契约和完整的运行路径。

| 能力 | 已有基础 | 需要补足 |
| --- | --- | --- |
| 材料与证据 | 受管 Artifact、PDF/Markdown 定位、Ink 快照与选区、来源回链 | 文本局部锚定、网页快照、生成内容溯源、统一输入包 |
| 来源发现 | A/B、覆盖记录、有界修订、部分结果、重验证 | 按需读取、跨轮次复用已有对象、局部事实和关系提案 |
| 图治理 | StableId/RevisionId、MapPatch、影响计划、来源登记与撤回 | 类型化暂存投影、身份连续、新对象引用规则、任务产物接受、统一生命周期 |
| 模型调用 | `LlmBackend` 的单次/流式调用和工具 DTO | 完整 Agent 运行适配、图片传递、真实反馈接续、执行中恢复 |
| 查询 | 材料读取、来源图与景观图投影 | 面向 Agent 的受限搜索、文本上下文读取、按版本的局部图查询 |
| 数学检查 | Lean 模块占位、EMIR 形式证据设计 | 固定环境中的检索和局部检查、可信状态与原文对齐分离 |
| 并发控制 | 部分用例活动锁、SQLite 事务、Ink 写入 epoch | 单活动调查与短提交协调器、读写依赖及集合守卫、恢复和迟到结果处理 |

现状以代码为准。比如 Desktop 已有 `list_discovery_runs` 和恢复审核入口，但一般发现运行仍主要在返回或取消后保存检查点；“已完成结果可重开”与“执行中崩溃后能恢复”是两个能力。实施前先校正文档中的旧描述，避免重复开发。

## 3. 首版可接受的简化前提

以下均为建议，需结合第 11 节的验收和第 12 节的决策确认。

| 编号 | 首版假设 | 简化的部分 | 仍需保留 |
| --- | --- | --- | --- |
| A1 | 一个 Workspace 同时只有一个拥有写权限的 Mathscape 桌面进程 | 不支持多实例并发治理同一库 | 进程级 Workspace 排他保护；第二实例只读或拒绝打开 |
| A2 | 一个 Workspace 同时只有一轮活动知识调查 | 不做多调查调度和多写入者合并 | 可有多个待续任务；用户可暂停当前轮再切换 |
| A3 | 探索期间不持有知识写锁；所有知识提交通过一个协调器串行处理 | 不做对象级长锁、CRDT、自动三方合并 | 依赖/写入前置条件、查询结果条件、短事务和幂等；无法精确验证的计划保守重验 |
| A4 | 数学对象允许暂时重复；身份归并由显式治理完成 | 不求解全局语义去重 | 标明对齐候选、歧义和适用上下文，保持旧引用 |
| A5 | 首版只集成一个 Agent 执行后端和一个可选 Lean 后端 | 不预建多后端兼容矩阵 | 小型执行契约、版本/能力探测、明确失败状态 |
| A6 | 知识清理优先可恢复的移除或退役 | 暂缓物理回收、压缩历史和复杂保留期 | 用户能清理列表；引用保护、停止写入和恢复规则明确 |
| A7 | 首版先做局部调查，同时保存学习观察和简单计划条目 | 暂缓自动掌握度推断、个性化路线优化、自动 R/D/T/X 挖掘 | 自评、实际作答、Agent 诊断和任务完成分别记录；局部成果可被长期计划引用 |

A1/A2 不意味着没有并发风险：平板、前端窗口、外部 Agent 子进程、在途工具请求和后台任务仍可能同时活动。简化依靠可执行的入口约束，不能只在说明中写“单用户”。

## 4. 对象与来源扩展

### 4.1 先分清记录职责，再决定哪些显示为图节点

不把每句对话、每次搜索和每个工具调用都加入默认数学地图。建议分为三组：

- 调查记录：目标、轮次、用户输入、待回答问题、上下文清单、工具回执。适合任务时间线和审计视图。
- 可引用内容：导入材料、手稿快照、网页获取快照、Agent 生成解释、用户补充说明。大内容复用 Artifact Pool，按需要建立定位。
- 知识对象：来源单元、数学声明、对齐、证据和未解决义务。达到相应条件后进入知识视图。

这三组可以有显式引用，默认图只展示与用户当前问题有关的投影。存储记录身份不等于默认可视节点。

### 4.2 建议新增或补全的最小记录

| 概念名（候选） | 职责 | 首版处理 |
| --- | --- | --- |
| `Investigation` / `InvestigationRound` | 长期问题与一次实际执行；目标版本、状态、累计预算、当前阶段 | 新增业务记录；一个问题可以有多轮，Agent 会话 ID 仅是执行映射 |
| `UserContribution` | 用户问题、纠偏、自评、回答及材料引用 | 文本直接持久化；手稿绑定快照/选区；记录实际提交者和对应问题 |
| `PendingQuestion` | 待用户回答的事项、原因、回答引用及失效状态 | 可选填、跳过或取消均明确记录；无回复不等于同意 |
| `ContextManifest` | 某轮或某份产物实际使用的输入、来源范围和版本 | 输入清单不可变；动态读取追加取得记录，产物绑定确切依赖清单 |
| `GeneratedArtifact` 的溯源记录 | 保存解释、例子、猜想说明或计划等生成内容 | 优先作为既有 Artifact 的产物类别和溯源关联，避免另造对象池 |
| `ProposedChangeSet` + 类型化暂存对象 | 待审的领域对象与变更计划；审查过程不充当另一套知识类型 | 替代通用 `CandidateRecord`；使用版本化领域 payload、预分配身份、待审计划和调查限定投影，见 §4.4 |
| `ToolExecutionRecord` | 工具参数摘要、输入版本、输出、环境、失败/取消与消耗 | 关键结果耐久保存，外部日志作为附件；大输出进入受管存储 |
| `AcceptanceRecord` | 对哪份产物/哪一版变更的接受或拒绝 | 扩展现有决定与回执思想，区分人工与明确策略接受 |
| `SemanticEntity` / `Alignment` 的最小实现 | 在有限领域保存精确声明及其来源对应 | 沿用 EMIR 概念；上下文不清的内容留在候选层，不提前建完整语义平台 |
| 最小 `DialectScope` / `LocalSymbol` / `LocalAssumption` | 来源中缓慢变化的符号和约定 | 直接使用 EMIR 的领域概念及差量方式；未解析状态和所需 Schema 扩展见 §5.4 |
| 最小 `ProofContext` / `ProofState` / `ProofTransition` / `Debt` | 局部假设、目标、推导步骤及尚未履行的义务 | 首版用于类型化的推导重建和纠偏候选；不要求 Lean 自动抽取或 R/D/T/X 识别，见 §4.5 |
| `LearnerStatusRecord` | 有来源的自评、作答表现及诊断判断 | 属于用户观察记录，绑定目标版本和任务范围；不改变共享数学可信状态 |
| `StudyPlan` / `RoadmapItem` | 版本化简单学习清单及条目进度 | 连接阅读范围、题目或调查；完成动作与理解证据分开，见 §4.6 |

暂存对象沿用相应领域 DTO，而不是把声明、关系和对齐都变成异构的“候选知识”类型。正文尚无法结构化时，保存为调查产物及未解决事项，不制造满足不了自身不变量的领域对象。提交/审查状态、对象生命周期、各轴可信状态分别记录；首版可保留有出处的自然语言解释，不能借“已保存”自动升级为精确共享声明。

### 4.3 Agent 原创内容如何成为可引用来源

按产物用途分流，去掉必须先经过来源单元再产生数学候选的暗示：

```text
用户问题、材料、手稿、已有声明 → 调查轮 / 工具执行
                                  ├─ 解释、例子、教学长文
                                  │    → GeneratedArtifact
                                  │    → 按需 SourceSpan（用于定位与追问）
                                  └─ 辅助声明、推导步骤、缺失条件
                                       → 类型化暂存对象与 ProposedChangeSet
                                       → SemanticEntity / ProofTransition / Debt
两路都保留生成运行、实际输入和 Evidence；经接受才进入相应的活动知识视图。
```

约束：

- “来源真实存在”和“数学内容正确”分开。准确定位一段 Agent 输出，只能证明它说过这段话。
- Agent 给出的新引理不要求伪造外部文献。保留其生成来源、假设、推导依赖和核验结果即可进入候选；正式晋升遵循类型与证据门槛。
- 解释性文本默认只保存产物及必要定位，不自动分割为 `SourceSemanticUnit`；结构化推导直接使用领域对象，`Evidence.llm_analysis` 与后续工具证据并存。只有满足操作契约后才考虑 Macro/X，不能把一段有用解释直接标作 X。
- 这是一项产品默认策略，不把 `SourceSemanticUnit` 重新定义为“只允许外部出版物”。若用户以后将某篇生成解释整理成明确的笔记材料，可经独立摄取/审核建立来源单元，标明生成来源；它不因此成为独立数学佐证。默认来源视图应区分外部材料、用户材料与生成产物。
- 一段解释可以同时引用教材、手稿和检查结果；这些是不同来源角色，不能把不同材料的片段拼成一个伪造的原文单元。
- 重新读取本 Agent 或其他 Agent 的转述不产生独立验证。引用链应保留共同根依据，审查结果记录实际独立性。
- 用户纠偏追加新记录并指向被纠正内容。它可改变任务意图；涉及数学事实时，还需适用的证据检查。
- 生成内容可以先作为任务产物存在；仅在需要引用、检索复用或持久图关系时创建相应锚点和知识对象。
- 若用户只描述目标而未要求整份草稿上传，输入包只包含本轮明确选定的文本和手稿版本；平板继续书写不会自动改变已发送图片。

EMIR 中的 `created_by`、`generation_run` 和 `Evidence` 应被复用，但溯源记录不能只依赖 Artifact 的首次创建者。同样字节可能来自不同取得/生成事件：池内字节可去重，每次生成或取得的作者、URL、输入、运行身份仍分别记录。

### 4.4 类型化暂存、身份连续与候选投影

建议保留一份审查过程记录 `ProposedChangeSet`，包含不可变提案版本、依据、现有对象前置条件、暂存对象、拟执行操作和审查决定。`MapPatch` 表达操作，不单独承担任务状态、拒绝理由和历史产物的职责。服务端在提案有效后编制补丁；不能直接执行外部 Agent 给出的任意 MapPatch。

- 已符合候选种类结构要求的对象，由服务端在相应身份规则内预分配 Stable ID 和暂存 revision；`(request_id, local_ref)` 幂等绑定同一分配，跨轮次可引用。来源对象优先查询/复用旧路径的确定性身份，不能另用随机 ID 绕开重复登记。接受后尽量保留 Stable ID，生命周期、可信状态或内容变化产生新 revision；解释和批注仍可打开旧暂存 revision。
- 暂存修改已有对象时，记录原 revision 与一个候选 replacement，不能覆盖活动版本。接受决定绑定具体提案版本和计划指纹；暂存内容改变后必须重新检查，旧决定不能接受新内容。
- 若后续解析发现对象已存在，保留预分配候选及显式的 reuse/identity-resolution 记录，标明接受结果实际采用哪个对象；不能静默重编号并让旧引用消失。真正拆分含义仍遵循 §5。
- 查询默认读取活动知识；显式指定 investigation 和暂存集合版本时，返回活动快照与经检查的暂存内容组成的只读投影，每个节点/边标明 accepted/staged、对象 revision 和提案版本。跨调查默认不暴露暂存候选。
- 目标缺失、同一对象有多个互斥 replacement 或基底已变化时，返回阻塞/冲突，不按最后写入者任取一个叠加。尚未满足领域不变量的草稿只能在提案诊断中出现，不能伪装成合法图节点。
- 正式提交不得留下只指向暂存对象的引用：必须共同接受必要依赖，或已存在可用目标。拒绝提案后，其他依赖它的暂存提案标为受阻；历史解释仍可查看被拒绝的候选。

这里的 staged/pending_review 是提案存储状态；当前 EMIR/代码的 `curation_status` 没有 `candidate`，可使用既有 `LifecycleStatus::Candidate` 与 `curation: raw` 表达相应维度，不能混用成一个“候选”总开关。

### 4.5 首版纳入局部证明状态与纠偏

手稿纠偏需要表达“用户在什么假设下，从哪一步走到了哪一步、缺什么条件”。建议首版在限定数学样例中实现 EMIR `ProofContext`、`ProofState`、`ProofTransition` 和 `Debt` 的最小候选路径：

- `ProofContext` 保存局部假设、见证、变量和分支差量，复用慢变化的来源 scope；不同分支不能共享一份可变假设表。
- `ProofState` 的目标使用有出处的 `ExpressionCandidate`，可保留文本/LaTeX 与未完成解析，形式环境允许未知。未知目标不能冒充已经类型检查的表达式。
- `ProofTransition` 保留输入/输出状态集合、使用的依据、手稿快照选区、生成运行和重建证据；不强制所有证明构成单链，也不假定多个目标互不耦合。手稿定位作为 typed evidence 引用，不硬塞进 `source_unit` 字段。
- “用户写了这些笔迹”与“Agent 将其解释为这一步推导”分开。解释有歧义时保留候选或问用户，不能把重建结果当成用户亲自陈述的事实。
- 缺少条件、类型不清或尚无证明，分别生成适当的 `assumption_debt`、`typing_debt`、`proof_debt`，而不是一概标错。只有反例或其他证据支持时才记录步骤被反驳；义务的处置状态与命题/步骤的正确性状态不能混为一谈。

首版只需可查询的一段局部推导及其义务，支持点击诊断返回具体手稿。Lean、自动证明状态提取、宏发现和完整 R/D/T/X 可以后续增强；未形式化的步骤保持相应可信级别。

Debt 的最小 DTO 也需要明确版本化：R/D/T/X 的现有示例要求 `generated_by` / `required_for` 指向 Operation，但中性 ProofTransition 阶段可能尚未识别算子。应定义可指向推导步骤、候选声明或上下文检查的类型化义务关联，并保留生成运行；不能为了登记缺失条件伪造 D/T/X Operation。核验完成后再关联真实操作及偿还证据。

### 4.6 学习观察与最小学习清单

建议新增用户侧的 `LearnerStatusRecord`，以追加观察保存 `target(id, revision)`、适用任务/技能范围、观察类别、报告者、时间及证据。用户自评、习题作答结果、Agent 诊断是不同类别。`confused`、`practicing`、`understood` 可作为界面摘要，但 `understood` 必须说明是谁报告、依据什么；一次正确作答不自动代表掌握全部变式。

`StudyPlan` 绑定长期目标及版本，包含有稳定条目 ID 的 `RoadmapItem`；条目可以指向阅读范围、题目、声明或某次 Investigation。首版支持明确次序、简单前置引用、待开始/进行中/已完成/跳过，并记录完成事件和关联学习观察。修改计划产生新版本，旧作答和观察不随条目重排丢失；任务完成不自动修改共享知识或证明状态。

这些记录首先显示在任务和学习计划视图，不要求作为默认数学图节点。目标语义发生变化或被拆分后，原学习观察保留原 target revision，是否适用于新对象需重新确认。首版不实现自动诊断评分、能力向量或路线优化算法。

## 5. 数学身份、歧义与语义稳定性

### 5.1 Stable ID 的含义

`stable_id` 标识系统中的一个受治理对象；`revision_id` 标识该对象的一个不可变版本。Stable ID 不承诺“现实数学里每个含义只有一个 ID”，也不允许一个对象的含义在修订中任意漂移。

需要区别四种身份：

1. 字节身份：内容哈希相同的文件内容。
2. 来源发生位置：某份固定材料中的某个位置；相同文字在不同来源中仍是不同发生。
3. 来源表达对象：定义、定理、习题等局部言语单元，允许边界识别被修订。
4. 数学语义身份：受理论、binder、假设、表达式和解释环境约束的对象。

语义对象 ID 建议由服务端分配并稳定保留；规范化指纹用于检索与提示重复，不作为自然语言数学含义的自动同一性判据。旧 A/B 按材料和范围生成的来源 ID 继续兼容，不在本阶段整体重算。

### 5.2 常见冲突与候选处置

| 情形 | 例子 | 建议处置 |
| --- | --- | --- |
| 多种文字表达同一精确声明 | 中英文、符号替换、两种量词写法 | 来源分别保留；提出 `expresses` 或带 binder 映射的对齐，验证后复用声明 |
| 相同词语在不同环境中含义不同 | 不同书对“环”是否含单位元的约定不同 | 拆开上下文中的对象；标签可相同，查询展示作用域 |
| 定义等价或逻辑等价 | 连续性的不同刻画 | 使用有类型的 Alignment；等价证据不自动授权合并 ID |
| 同一表达有多个尚未确定的解释 | “正定”未明确实/复数域及算子约定 | 保留同一来源表达和多个解释候选；不把多个不兼容含义装进一个已确定声明 |
| 原 Stable ID 被错误用于两种含义 | 同一声明后来发现混入有限维与无限维版本 | 将旧对象标为有争议/被替代，创建清晰的新对象并记录拆分；逐条审查依赖，不自动分配旧引用 |
| 不同 ID 实际重复 | 两次调查各登记了同一精确定义 | 暂时允许重复；首版用已审核的对齐和视图分组，延后破坏性归并 |
| 内容本身矛盾 | 同一上下文下相反的两个断言 | 记录冲突和反例/证据；不按新旧、票数或模型自信覆盖其中一方 |
| 来源范围重新切分 | 两句定义被拆成定义与说明 | 保留旧锚点；新范围产生新定位，记录替代/细化候选，不能重写旧证据 |

### 5.3 修订与新对象的界限

- 修改标签、排版、展示说明，且精确含义未变：可用原对象的新 revision。
- 对缺失上下文的候选补充解释：产生新的候选 revision，保留原文与旧假设；晋升前再决定数学身份。
- 已接受声明改变必要假设、binder 类型、结论或解释环境：默认提出新语义对象，并用 `specializes`、`generalizes`、替代等关系表达变化，不能以“修正文案”静默改变被引用定理。
- 拆分是治理事实，不等于数学关系；替代也不等于逻辑等价。需要为这类治理关系制定独立的类型和引用规则。
- 历史证据总是能够指向原对象和原 revision；视图可以推荐替代对象，但不能把旧引用自动跳转为新含义。

### 5.4 直接复用 EMIR 上下文与不完备状态

正式语义提案至少携带：适用领域/理论、自由变量和类型、已使用假设、符号解释、原始表达、引用依据，以及明确未解决项。字段尚不能充分解释时，保留候选并提出需要的上下文，不能以空壳 Theory/DialectScope 表示已完成消歧。

取消另建“轻量上下文、以后迁移”的方案，首版直接以 `DialectScope`、`LocalSymbol`、`LocalAssumption`、`ProofContext` 和 `Debt` 的领域边界设计最小 DTO。慢变化的书籍/章节约定属于 DialectScope，单步引入的变量或见证属于 ProofContext；表示绑定依然是独立职责。文本/公式保留在表面表达和 ExpressionCandidate 中，解析 AST 未完成时明确记录，不更换成只有字符串的第二套 scope。

最小实现需要明确的版本扩展：现有 EMIR 中 `DialectScope.source_edition`、`introduced_by_unit` 和 `ProofContext.dialect_scope` 有必填引用，不能仅删字段或伪造对象满足 Schema。优先复用已有 `SourceEditionBinding` / `DialectScopeBinding`，为候选上下文定义 unresolved/uncontextualized 分支，并记录 Debt；涉及新增字段或将必填引用改为绑定类型时须更新规范和 Schema。无法满足新候选契约的草稿只保存在提案诊断中，不进入合法领域投影。`bound` 也不等于所有上下文义务已解决。

来源中的直接约定、继承约定、惯例和推断对应 `LocalAssumption.explicitness` 的 `explicit | inherited | conventional | inferred`；后两者须记录尚未确认的适用性及相应 Debt。用户提出“这一轮请假定……”属于任务假设，实际来源记录为 UserContribution，不能仅靠 explicitness 推断是谁作出的陈述。用户自评只改变学习观察，不修改共享数学声明。

补充一项标准工具动作：对当前未绑定符号或假设，返回 `resolved / ambiguous / not_found / needs_more_scope`、候选定义位置、实际搜索范围和证据。Agent 可沿目录、前文引用或已有 scope 查找上游约定，只锚定命中片段，记录它们在本次输入清单中的 `context` 角色；这不是在 SourceSpan 本体中增加通用角色字段。多重定义和局部遮蔽不能任取最近命中。后续补齐 parent scope 或差量时创建新 revision，并重验依赖该上下文的暂存提案。

`effective_context_hash` 绑定实际已知的父 scope/context revision 和差量，结合绑定状态与未解决义务解释其有效范围；相同哈希不能作为“没有遗漏其他约定”的证明。尚未知的父上下文保持缺口，不为了连出一棵完整树而补造 scope。

论文中的经验结论、物理建模假设和数学推论也应分别标明。尚未数学化或超出当前工具覆盖的内容可以保留为来源或待研究事项，不要求为了形成统一地图而补造形式声明。

只做必要的局部完整性：

- 本次使用的关键前提不能被隐瞒；未知时明确留缺口。
- 已正式提交的引用指向既有有效对象或同一提交中的新对象。
- 暂未找到目标的引用保存为未解析候选，不创建指向不存在对象的正式边。
- 查询返回“此范围尚未调查”“未发现匹配”或“存在不兼容候选”等状态；不能从稀疏图中推导不存在定理、关系或前置条件。

## 6. 惰性扩展与 A/B 的兼容路径

### 6.1 三个范围与两种产物

每次任务应区分：允许读取的材料范围、本次实际读取和用作证据的范围、允许提交变更的对象范围。读取整段前文以理解记号，不意味着必须把整段建图，也不意味着可改动其中所有对象。

调查产物可以是解释、追问、候选或局部知识提案。来源整理产物仍可以是 A/B 的 UnitSet 与来源事实。A/B 作为可选的有界工具保留，适合批量整理、重建局部来源目录和检查覆盖。

### 6.2 局部提交的候选接口

接口应支持以下最小动作：

1. 从固定文本/手稿/网页快照构造并校验证据定位；
2. 提议一个来源单元，或给已有单元补充明确事实；
3. 引用已有对象与本次临时对象，提议一条关系或 Alignment；
4. 保存解释、声明或诊断候选及其未解决项；
5. 生成影响计划，经接受后提交，返回可重试的回执。

候选请求可包含 `request_id`、`investigation_id`、`round_id`、`input_refs`、`existing_refs(id, revision)`、`proposed_objects(local_ref, typed_payload)`、`proposed_relations`、`unresolved`。服务端分配暂存身份，建立 `ProposedChangeSet`、读写前置条件和必要的查询条件守卫；不能只相信 Agent 自报的依赖清单。这只是讨论形状，Agent 不提供权威 revision、人工身份或“已通过核验”的可信对象。

同一批可以原子创建锚点和引用该锚点的单元；不强迫 Agent 为每个节点单独发一次提交。多轮已经提交的有效结果保留，后续失败不回滚整次调查；最终结束状态报告哪些产物已提交、哪些仍为候选。

### 6.3 保留与改造边界

| 设施 | 复用方式 |
| --- | --- |
| Schema/DTO | 保留旧版本；局部任务新增明确契约；小批提案不伪造 discovery run 或 coverage |
| Selector/OccurrenceResolver | 继续负责准确定位与受限规范化；支持不同输入后端，不放松错误定位检查 |
| 验证器 | 提取证据、引用、版本等共用规则；A/B 的全范围 coverage 和冻结目录规则保留在专用路径 |
| SourceRegistrationPlan | 原路径继续重放；新增路径可引用存储中的对象；局部来源与后续 A/B 经过 §6.4 的对照处理，共用下层影响计划与提交不变量 |
| MapPatch/回执 | 复用事务、幂等和审计；接受依据增加任务产物及实际主体，不冒充人工操作 |
| LlmBackend | 继续支持单次/流式专用任务；完整 Agent 另接 `AgentExecutor` 一类适配器 |
| Prompt | A/B 提示保留；调查提示控制策略；身份、权限和证据约束由服务端执行 |
| 测试与 fixtures | 保留旧记录回放；新增局部提案、跨轮复用和故障恢复样例 |

“解码 → 证据/上下文/结构检查 → 生成计划 → 接受 → 提交前重验证”继续成立。确定性验证只能验证它实际掌握的约束；Schema 合法、引用存在、原文相符均不等于数学论证正确。

### 6.4 局部来源与后续 A/B 的衔接

接受“批量发现应了解已有局部来源”的建议，但不以强制创建章节父节点或按重叠自动合并解决问题。

1. A/B 输入准备与局部提案准备都查询同一 Artifact 快照及目标范围内已有单元、定位、revision、结构与争议状态，形成可重验的来源目录上下文。已有身份和历史受保护；其分段边界作为先前判断展示，不视为永远正确的不可变分段。
2. 提案后进行确定性对照：精确相同定位的 SourceSpan 可复用；已知同一来源单元优先绑定原 Stable ID。追加 parent、标题或事实是原对象的显式修订，仍按共享采纳、版本和影响计划规则检查。范围或结构不一致时提出细化/替代/争议计划，不能静默覆盖。
3. `parent_unit = null` 可以表示目前未绑定组织归属，不意味着原文截断。只有实际文本在单元边界处缺失，才标记 `left/right_truncated`；不能将组织结构尚未发现混入 `completeness`。有证据的章节锚点可以复用，但不是每个局部单元的登记前置条件。
4. 证据跨度允许合法重叠：章节包含定理、多个解释引用同一段、关系证据覆盖单元等均可能合理。重叠比例用于候选检索和诊断，不证明语义同一。确认重复后要求复用/修订；存在竞争性切分时保存争议，不无声地增加第二个等价活动单元，也不靠伪造 parent 放行。
5. 正式来源 `proof_step` 沿用 EMIR 的 proof 归属约束。若尚不能识别所属证明，可先建立片段 SourceSpan 和候选 ProofTransition，而不是为满足归属凭空创建 proof/section。
6. 来源范围对照属于集合条件：准备时没有重叠单元，不代表提交时仍没有。提交时重新检查相关材料范围与单元结构，或使用覆盖这类变化的目录版本守卫；详见 §8。

旧 A/B 身份按 Artifact 与范围生成。新增路径在分配身份前先查询并复用这一身份空间；范围冲突不能通过随意生成新 ID 绕过治理。跨来源数学重复的容忍策略与同一来源的重复登记控制分别处理。

## 7. 工具能力草案

### 7.1 工具目录

以下名称是能力分类，不规定最终 RPC/MCP 名称。先实现用例服务，再由所选执行适配器连接，不把通用 Tauri 命令集直接开放给 Agent。

| 能力 | 首批动作 | 必须返回或记录的内容 | 优先级 |
| --- | --- | --- | --- |
| 材料目录与文本搜索 | 列材料、查目录、按关键词/符号搜索、按位置读取、扩展前后文 | Artifact/版本、精确位置、匹配原因、截断与读取范围；搜索命中不是已验证事实 | 首个调查前 |
| 上游记号与假设寻址 | 查符号候选定义、沿目录/引用读取约定、解析 scope 继承与遮蔽 | 有出处的 LocalSymbol/LocalAssumption 候选、scope 版本、实际搜索范围和未解决 Debt；不盲目扩扫整章 | 首个调查前的最小上下文路径 |
| 内容 scan | 有界扫描目录、标题和章节结构，必要时局部来源发现 | 扫描范围、处理状态、候选位置、产物和缓存版本；不承诺穷尽 | 先做最小版本 |
| 图查询 | 按 ID/版本读取、搜索、局部邻域及调查限定暂存投影 | 对象/提案版本、生命周期、可信状态、关系角色、查询边界及必要守卫；暂存不冒充已接受 | 首个调查前 |
| 用户输入与反馈 | 读取实际用户补充、提出问题、接收带 question_id 的回答、关联手稿 | 提交者、时间、目标任务、被纠正对象、固定输入版本；Agent 不能制造用户回答 | 首个调查前 |
| 手稿与图像 | 选择快照/区域、渲染 PNG、读取页和笔迹定位 | 输入快照、渲染配置/版本、页坐标与像素映射、图像摘要；验证后端实际收到了图像 | 首个调查前 |
| 推导重建与义务查询 | 提交/读取局部状态、步骤、假设和 Debt，回到手稿位置 | 区分原始作答、Agent 重建、未知条件与反例；非形式步骤明确未核验 | 首个手稿纠偏场景 |
| 学习记录与简单计划 | 记录自评/作答观察、创建与调整条目、关联调查和完成事件 | 目标 revision、报告者、证据与任务范围；完成不自动等于理解 | 首个学习清单场景 |
| 局部知识提案 | 锚定证据、提交候选、预览变更、接受后提交、查询回执 | 引用闭合、影响范围、待核验事项、实际接受依据和幂等结果 | 首个调查前 |
| 联网资料检索 | 搜索/读取 MathOverflow、Mathematics Stack Exchange 及任务允许的其他来源 | URL、站点/帖子/回答身份、作者、获取时间、可用的编辑版本、取得内容快照 | 首个联网场景前 |
| Lean 检索与检查 | 检索候选声明、读取类型和前提、检查局部代码/目标、取诊断 | 固定 Lean/mathlib 环境、实际代码、imports、目标、诊断、假设/公理及检查范围 | 可独立实验；不阻塞纯解释场景 |
| 任务控制 | 查询状态、取消、暂停、恢复、预算与工具历史 | 权威任务状态、轮次 generation、已发生副作用与未确认结果 | 首个调查前 |

优先做简单、可解释的文本/结构检索。全文向量库、符号检索引擎和自动全书索引只有在实际命中率或成本成为问题后再引入。检索缓存绑定材料及检索器版本，不能用旧缓存冒充最新材料。

知识查询默认优先返回可用的已接受对象；候选、退役对象和历史修订通过显式范围参数查询，并始终携带状态。材料搜索可以直接读取授权范围内尚未建图的内容，不受“是否已接受为知识”限制。

### 7.2 用户输入、手稿与纠偏

用户可以在 Agent 执行时继续书写和补充信息。这些内容先成为独立输入记录；在明确的下一轮输入边界纳入调查，不能在一次检查中途悄悄替换上下文。主动纠偏可触发暂停/取消当前轮，再建立绑定新输入的新轮。

手稿仍采用当前单写入者与 outbox 协议。发送给 Agent 时固定已确认前缀；若设备还有未同步笔迹，提供“等待同步后提交”或明确只提交已同步内容的选择。不得把设备尚未确认的笔迹显示为已进入分析。

解释中的手稿引用打开当时快照和区域；当前草稿可以继续编辑。文字转写或 OCR 属于派生产物，保留不确定性和图像回链，不替换原笔迹。

### 7.3 联网资料的边界

- 搜索摘要只用于选择阅读目标。需要作为依据的内容，应保存实际读取到的帖子/回答快照及定位；仅保存 URL 不足以稳定回链。
- 区分问题、不同回答、评论、后续编辑与转述。点赞或站点采纳状态只能作为来源元数据，不能升级数学可信状态。
- 无法读取或页面已失效时，返回失败/缺失状态；不能让 Agent 凭记忆补成已抓取原文。
- 取得记录保留可获得的作者、引用和权利信息，后续展示沿用来源归属。实施时再核实各站点当前接口、限制和使用要求，本草案不指定爬虫或宣称拥有再发布权限。
- 外部页面是材料。其文本中的工具指令、角色声明和代码片段不获得本地执行或提交权限。
- 默认联网查询不自动附带整份私人材料或手稿；任务配置明确可联网范围。搜索、受管快照和正式来源登记分别记录。

### 7.4 Lean 的最小可信边界

不预先接入多个 Lean 服务。先用一个固定工程验证：检索声明、展示实际前提、对一段局部推导取得可重现检查结果。每次执行有资源边界，可取消；检查代码仅在任务工作目录运行。

编译成功不能单独作为无条件证明回执：应记录目标声明、是否存在占位证明/未解决义务、依赖假设和公理、实际工具环境。类型检查、目标信息、数值实验、完整证明证书采用不同的结果类别。Lean 证明成立与“忠实表达用户题目”分别审查。

## 8. 单用户条件下的并发简化

### 8.1 推荐：单活动调查，探索期版本化读取，提交期短锁

采纳 Argon 对长周期界面阻塞的担忧，修改 A3：一个 Workspace 仍只运行一轮 Agent 调查，但其读取、模型推理、网络查询和 Lean 检查不占知识写锁。用户可编辑知识对象；所有人工、A/B、Ink 证据与 Agent 提交经过同一服务端协调器，在短的临界区/事务中串行检查并写入。

这是乐观并发检查（OCC）的有限应用：读取绑定版本，提交验证前提，冲突后重新检查而不自动合并。它不要求多个 Agent 并行执行，也不能只靠 SQLite 将写入排成先后来解决读到旧状态的问题。

每次工具读取用短只读事务取得一致结果并保存引用。跨调用的 ContextManifest 是实际读取过的版本集合，不宣称数分钟调查期间共享一个完整数据库快照，不保持长时间 SQLite 读事务。同一对象若出现不同 revision，不悄悄拼接为一个上下文：返回版本变化，明确重建本轮相关依据或暂停。

不可变 Artifact 字节和历史 revision 可以继续引用；材料的可用性、活动对象与最新任务意图仍在接受时检查。手稿、日志和生成产物的追加不改变本轮已绑定的证据；物理清除另受保留引用约束。

输入引用应标明是明确选定的历史证据，还是要求仍为当前有效版本的前提。前者检查原版本与存储可用性，不能因出现新 revision 自动判错；后者检查当前 revision 和治理状态。写目标始终校验当前前置条件，不能借“历史引用”覆盖用户的新修订。

### 8.2 操作矩阵

| 操作 | 活动轮执行中 | 等待用户/审核或已暂停 |
| --- | --- | --- |
| 阅读材料、查看图、打开历史 | 允许 | 允许 |
| 平板书写、自动同步、保存固定快照 | 允许；不改变当前轮已绑定的输入 | 允许 |
| 用户补充问题、纠偏 | 持久接收；提示下一轮纳入或先暂停 | 纳入新上下文后恢复 |
| 当前轮工具提交局部变更 | 允许，校验依赖、当前权限与接受决定后短事务提交 | 旧执行授权失效；人工接受走独立提交入口并重验 |
| 手工修改/删除知识对象、撤回登记 | 允许走同一短提交通道；改到调查依赖会导致相关计划待重验 | 允许；恢复和接受时核对版本、状态及查询条件 |
| 启动另一轮 A/B 或调查 | 拒绝并显示当前任务；用户可先暂停 | 可以切换，原任务保持待续 |
| 网络下载、转换等后台工作 | 可生成隔离暂存产物；正式登记走同一短提交通道 | 经协调器登记 |

等待用户可能持续几小时。进入 `awaiting_user` 或 `awaiting_review` 前保存检查点并撤销本轮执行授权，释放活动调查名额；此时没有持续占用的知识写锁。回复到达不会自动抢占正在运行的其他任务。

首版等待审核时停止本轮执行，便于形成明确的输入和提案版本边界。用户接受时重新验证计划；继续执行则取得新 generation。接受某个产物不自动启动新轮或授权其余待审变更。

### 8.3 已知引用检查之外，还需检查集合条件

比较 `existing_refs ∪ ContextManifest.entity_refs` 的当前 revision 是必要条件，但不能证明提交一定安全。例如，准备删除 A 时没有任何引用者；后来新增 B→A，A 自身的 revision 可以完全不变。创建来源单元前的“该范围没有已有单元”、新增 parent 前的无环检查、撤回登记时的共享采纳集合也有同类问题。

服务端为每份提案收集三个部分：

1. **读依赖**：工具实际返回并作为本次依据的对象/Artifact/暂存对象版本、scope/context 父链、用户目标和证据绑定；首版可保守包含该提案上下文中的全部读取，不能仅由 Agent 选择申报。
2. **写前置条件**：被修改对象的 expected revision、生命周期、接受状态、权限与目标暂存提案版本；Agent 没有读取过的写目标也必须检查。
3. **集合与结构条件**：引用者、采纳集合、范围重叠、身份占用、parent 无环以及跨对象约束。为有限的工具类型定义可重查的 query guard（查询范围、过滤条件、完整结果或签名），并在提交事务中复核；有界/截断结果不能用来证明“没有其他对象”。

首版不需要通用谓词锁或全库依赖引擎：已知类型采用范围查询/结构校验，昂贵或尚无完备守卫的计划使用全局知识版本作为保守后备，变化时重新预览。不得把这个后备应用于全部简单提案；也不得因为缺少守卫就按“已读节点没变”直接放行。未来只有确有需要时才增加每材料/每索引的细粒度版本。

删除、撤回、身份复用和来源重叠等提交必须在同一短事务/受控临界区内重新检查真实当前约束。外部模型、网络、Lean 以及大文件计算在事务外完成并形成绑定输入的检查记录；事务内重验它们依赖的版本、存储可用性和记录身份。不保证固定毫秒数，需用实际数据测量。

无关变更不应使有完整依赖/守卫的提案过期；依赖变化时返回具体对象或查询条件和差异。先确定是可以重新生成计划、需要重新接受，还是确需重新调查，不能把所有冲突都变成整轮 LLM 重跑。普通全文搜索“未命中”只表示本次检索结果，仍不构成全局数学不存在的断言。

### 8.4 执行授权、恢复和最低保障

1. **入口一致**：协调器在后端覆盖所有正式写入。新对象种类要提供自己的引用枚举和提交校验，不能仅实现读取 DTO 就开放写工具。
2. **迟到结果隔离**：服务端签发 round generation，取消、暂停或重启使旧执行授权失效；授权由适配器持有，不能信任 Agent 自报。旧请求只可留诊断，不能继续提交。
3. **提交与撤销原子排序**：授权、依赖和当前约束检查与提交在同一受控临界区/事务条件下判定。已经提交成功的操作保留回执，取消不假装撤销它。
4. **恢复检查**：根据检查点恢复业务状态和暂存对象；重新读取实际依赖的状态及守卫，必要时重建上下文。不能因为后端成功恢复会话就跳过检查。
5. **幂等与对账**：同 request_id 的成功重试返回原回执；未知结果先查询，不重新分配对象 ID。新授权可只读查旧回执，不能借查询重执行已撤销写入。
6. **崩溃收尾**：保持单桌面写进程与 OS 级 Workspace 排他保护；重开识别中断轮并废止旧授权。外部子进程即使残留也不能直写数据库/对象池。

仍不做多调查并行、自动合并和分布式一致性。原先的轮次级知识独占锁不再是默认方案；若有限工具的守卫尚未实现，可在明确的受限实验中要求先暂停编辑，但应标注限制，不能宣称已经完成上述并发契约。

## 9. 生命周期、删除与派生产物有效性

### 9.1 首版候选规则

| 用户意图 | 首版语义 | 依赖处理 |
| --- | --- | --- |
| 从工作列表清理任务或材料 | 可恢复的归档/移至回收区，停止普通检索推荐 | 历史引用继续可解析，显示已移除状态 |
| 丢弃手稿草稿 | 停止设备写入，文档进入可恢复的删除状态，移出活动列表 | 已有独立快照和被引用证据保留；旧队列不得自动复活文档 |
| 删除未引用快照或产物 | 逻辑移除，首版保留字节 | 检查任务、候选、接受记录和历史引用，不只查可见图 |
| 清理被引用快照/材料 | 展示依赖并允许从活动列表移除 | 不静默破坏仍存续的回链；明确解除/处理引用后才进入后续彻底清除讨论 |
| 删除来源/语义图对象 | 复用或扩展退役/拒绝/替代治理 | 根据正式引用规则处理依赖，不把查询隐藏当作领域删除 |
| 撤回一次接受或登记 | 追加撤回决定，按实际采纳范围处理 | 保留共享对象、后续修改与历史决定 |
| 永久擦除和空间回收 | 单独后续阶段 | 定义活动引用、历史留存、任务保留引用和文件回收的完整规则 |

归档、可恢复删除和退役的 UI 标签需要按对象明确。首版应直说“已从活动列表移除、可恢复，存储空间尚未释放”，不使用会让用户误以为已永久擦除的提示。

恢复已删除手稿要显式重新取得写入权；旧 epoch 不因恢复而重新有效。原平板未同步内容可按当前恢复草稿路径另存，不自动合并到恢复后的文档。

### 9.2 依赖与有效性

保留两种状态：历史上是否可以复现，以及当前任务是否仍适用。旧解释引用旧题目仍可复现；用户将问题条件改掉后，该解释对新任务可能需要重检，不必宣称旧结论已经错误。

首版产物保存可枚举的依赖，包括 Artifact/对象版本、用户输入版本、暂存提案版本、工具环境及采纳决定。提交检查还包括 §8.3 的 scope/context 依赖和集合守卫，不能仅保存最外层几个节点就声称捕获全部前提。读取/恢复/接受时检查有效性；首版不要求实时重算所有派生结果。

暂存对象、学习观察和 RoadmapItem 也参与引用与保留检查。拒绝一个提案不自动删除仍被历史解释或学习记录引用的产物；学习目标被拆分后，计划可以提出重新绑定，不能静默转移旧的“已理解”状态。

长期不应只在 JSON 正文里藏引用：每一种正式加入的对象都必须提供版本化引用枚举规则，供校验、删除影响分析、备份和未来 GC 使用。回收器遇到未认识的对象类型时应保留数据并报告，不能据“没有查到引用”清除。

首版保留所有历史字节是降低复杂性的明确取舍；若用户要求真正擦除私人材料，这一取舍不满足需求，需提前设计完整的删除及外部副本处置边界。

## 10. 调查记录与执行适配契约

建议保留三个层次：`Investigation` 表示用户问题，`Round` 表示一次受控执行，外部 session/turn 表示后端实现。长任务可以更换后端会话，业务记录仍属于同一问题。

最小任务状态：待启动、执行中、等待用户、等待审核、已暂停、本轮完成、失败/已取消。用户是否认为问题已解决、是否完成练习、Agent 是否怀疑某项知识缺口，分别记录，不能复用执行状态。

执行适配器至少表达：启动、流式事件、工具请求、结构化产物、请求用户输入、取消、恢复/重建、错误和实际消耗。恢复从业务检查点重建输入；不承诺外部进程可以精确重放每个内部推理步骤。模型/后端不报告的成本标为未知，不能按零消耗继续无限运行。

输入包绑定原始用户意图、目标版本、材料与手稿选择、已知对象版本、未解决问题、读取授权和预算。动态扩展材料通过工具记录，不靠无限扩充一份可变 `plan.md`。计划允许修改，任务目标和接受标准的变化必须显式记录并让用户可见。

关键检查点至少包含：发起工具前的请求身份、工具完成回执、暂存对象与提案版本、进入等待状态、接受/提交结果。候选可以在本次调查的暂存投影中跨轮次查询；恢复后须重新校验基底，不直接叠加旧补丁。禁止把一份包含“已校验”字段的外部 JSON 反序列化为可信对象。

首版接受策略建议：只读读取、任务记录、隔离产物和未晋升候选可自动保存；新知识对象及其重要修订/对齐集中提供可审核的变更计划；人工编辑、删除、身份归并和 verified 状态遵循各自更严格条件。以后可允许明确授权的低风险自动接受，但来源必须记录为策略接受，不能冒充人类确认。

## 11. 验证场景与补漏边界

| 场景 | 必须观察到的行为 |
| --- | --- |
| 只问教材中的一个步骤 | 读取必要片段即可解释和提交局部候选，不强制整章 A/B |
| Agent 创造一个辅助引理 | 保存生成来源、假设、依赖和检查结果；不伪造教材原句或自动标为已证明 |
| 用户用手稿纠正先前解释 | 新反馈绑定原问题；保留原笔迹、候选状态/转移与所缺条件；新轮看见固定快照并能回到具体步骤 |
| 当前页使用前文约定的符号 | 按需定位定义，复用来源 scope 并记录继承/遮蔽；未找到则保留 Debt，不伪造解析完毕 |
| 候选跨轮次查询并接受或拒绝 | 调查投影可遍历合法暂存对象；接受后身份连续或有显式 reuse 记录，拒绝后历史批注仍可解析 |
| “环”在两本书中约定不同 | 名称命中不自动合并；提示上下文差异，并允许候选对齐 |
| 两次调查得到重复声明 | 可查询到两者及对齐候选；不破坏任一旧引用，不要求自动完成全局去重 |
| 原对象后来被发现含义混杂 | 可提出拆分/替代计划，旧 revision 可读；不把旧依赖无条件指给某个新对象 |
| 执行中用户整理无关书籍 | 人工编辑可短事务提交；有完备依赖守卫的当前计划不因无关版本变化失效 |
| 执行中用户修改或移除所用材料 | 允许受控变更；当前计划接受时指出具体依赖变化，不能提交基于过时前提的当前结论 |
| 待删除对象提交前新增引用者 | 即使目标对象自身 revision 未变，也必须由集合/结构检查发现，阻止破坏引用 |
| 局部登记后运行整章 A/B | 复用已有身份，组织 parent 可后补；重叠引发对照而非自动合并，不能将缺少 parent 标成原文截断 |
| 等待用户时关闭应用，修改材料后再回复 | 原问题与回复不丢失；新轮重新绑定输入，过期提案不能直接接受 |
| 提交后丢回执，随后取消或重启 | 查得原回执且只提交一次；旧 generation 的迟到请求被阻断 |
| 搜索命中被编辑的在线回答 | 旧解释打开原取得快照，新读取形成新版本；采纳/点赞不变成数学认证 |
| Lean 代码能编译但有占位证明或假设不符 | 结果类别和缺口明确，不声称题目已被完整证明 |
| 局部图没有找到前置关系 | 报告查询范围和未调查状态，不声称没有前置条件 |
| 用户完成学习清单中的一道变式题 | 条目完成事件、自评和作答表现分别保存；可关联后续调查，不自动宣称掌握整个概念 |

补漏完成的判断是：一个真实问题能带着材料和手稿进入调查，工具能按需读取，候选有出处，等待/恢复可靠，局部提交可验证，用户能清理对象且不会破坏仍存续的引用。无需先完成完整语义推理器、全库去重、所有 Lean 工具、长程路线优化或动画 IR。

## 12. 建议推进方式与待讨论决策

### 12.1 推进顺序

1. **契约收敛**：确认简化前提、EMIR 最小上下文/证明候选的版本扩展、暂存身份、集合守卫及首版删除语义；列出已有实现和旧文档差异。
2. **小型能力实验**：选一个 Agent 后端验证图片实际到达、材料工具、追问、取消、恢复；以固定局部题目测试 Lean 可选工具。实验不直接写生产知识库。
3. **共用底座最小实现**：任务/反馈记录、输入包、类型化暂存与局部证据、引用枚举、短提交协调器、影响预览和回执。用一段手稿推导验证最小 ProofContext/State/Transition/Debt，用三步清单验证学习记录；继续兼容 A/B 与 Ink。
4. **首条调查实现与实机验证**：围绕第 11 节场景，验证成本、首轮响应时间、用户纠偏及是否帮助理解。依据结果决定扩大语义模型还是改善工具与交互。
5. **后续扩展**：仅在明确需求出现后增加多调查并行、自动冲突合并、物理回收、更多 Agent/Lean 后端、路线优化和 R/D/T/X 自动构建。手写 P3.2 继续暂缓。

工具和数据契约应与首个调查场景共同验证。这个阶段不会以“完成一个全能工作流平台”为交付条件。

首个从本草案拆出的近期交付线是 [手写笔记融入 Mathscape 笔记体系提案 v1](ink-notebook-integration-v1.md)：先完成手稿命名、回收站、NoteLink 和地图/阅读器入口，为后续调查输入复用用户手稿上下文。

## 13. Argon 评审的采纳记录（2026-10-16）

| 建议 | 判断与调整 | 边界 |
| --- | --- | --- |
| 1. 用最小 DialectScope 和 Debt 代替临时上下文，补上游寻址 | 采纳；§5.4/§7.1 改为直接沿用 EMIR 概念与差量结构 | 来源 scope 与证明局部上下文仍分开；未绑定引用需要明确版本扩展，不能删必填字段或造空壳对象 |
| 2. 预分配 ID、暂存 MapPatch，避免候选晋升断链 | 采纳身份连续与领域类型复用；§4.4 增加暂存投影和依赖闭合，移除通用 CandidateRecord | 仍保留提案/审查过程记录；MapPatch 本身不能代替拒绝、冲突、版本与历史管理；不合法草稿不叠成图 |
| 3. 分流解释文本与数学构造 | 采纳默认分流；§4.3 不再要求生成内容先经过来源单元才能形成数学候选 | 原规范没有规定 SourceSemanticUnit 只能来自外部教材；明确整理成笔记时可独立摄取，但不能借此把生成内容变成独立证明 |
| 4. 首版前移 ProofState/Transition/Debt | 采纳最小单步纠偏能力；§4.5 与验收场景补入 | 同时包含必要 ProofContext；重建始终是可修订候选，欠缺条件不等于已反驳，不承诺全自动形式化 |
| 5. 探索无锁、提交短锁与 OCC | 调整为建议默认方案；§8 保留单活动调查，开放人工编辑 | 仅比较已读 ID/revision 不够：还需写目标、scope 父链、共享采纳和新增引用等集合条件；未覆盖时保守重验，不保证零误失效 |
| 6. 局部来源与后续 A/B 融合 | 采纳已有来源目录注入和范围对照；§6.4 补入跨轮次复用 | 未发现 parent 不等于截断；跨度重叠不等于同一单元；保护已有身份，但允许显式修正先前切分，不冻结错误分段 |
| 7. 最小学习状态与路线条目 | 采纳；§4.6 补充观察记录、简单清单及跨调查关联 | 作为用户侧记录/计划视图，不强制进入共享数学图；自评、实际表现、Agent 诊断与条目完成不能折叠成一个掌握度布尔值 |

评审中的若干字段是建议性写法，需要与当前契约对齐：当前 EMIR v0.2 和 Rust `TrustRecord` 的 `curation_status` 没有 `candidate`，`provenance_status` 也没有 `inferred`；另一个 R/D/T/X 文档的 provenance 枚举更宽，不能直接混入现有 DTO。生成来源由作者、generation_run、取得/生成记录及 Evidence 表达，候选生命周期与对齐候选使用各自状态。`LocalAssumption.explicitness` 描述假设表达方式，不能替代用户/Agent 身份。Debt 的 `refuted` 与步骤/命题的反驳关系需要在 DTO 收敛时精确定义，不能因“存在漏洞”就自动赋值。

本次调整吸收了评审指出的产品和契约缺口，也保留单用户首版的范围控制；七项建议不等于一次性实现全部语义平台。
